# 발표 자료용 사실 정리

> 기준: `origin/develop` 최신 커밋 `6e1f408` (2026-08-19, Should 단계 F16·F12·F11까지 병합 완료 시점). 모든 항목은 실제 코드(`git show origin/develop:<path>`) 또는 `SPEC.md`/`OWNERS.md`/`CHANGELOG-INBOX/`를 직접 읽고 확인한 사실만 기록했다. `tasks.md`의 체크박스는 216개 전부 미체크 상태라 진행 현황 판단에 쓰지 않았고, 실제 코드 존재 여부로만 판단했다.
>
> 이 버전에서 갱신한 것: 이전 버전(83d9deb 기준)은 용어 사전·O·X 퀴즈(F16)·STT(F12)·TTS(F11)가 전부 미구현이던 시점 기록이라 지금과 크게 다르다. 이후 병합된 PR #11(용어사전+퀴즈)·#12(STT·TTS)를 반영했고, "← 처음으로" 상태 미초기화·"다시 설명해주세요" 선제적 오답 문구·`shared/llm-config.js` 콘솔 404 3건을 코드 수정으로 해결했다(Node 로직 시뮬레이션으로만 검증, 브라우저 확인은 아직).
>
> **이번(최종) 갱신**: STT(F12)/TTS(F11)를 실제 Chrome에서 QA한 결과 시연에 쓸 만큼 안정적이지 않다는 게 확인됐다 — TTS는 문장 앞부분이 잘리고, STT는 "듣고 있어요…" 상태 이후 인식 결과가 답변으로 안정적으로 이어지지 않는다. 발표용 MVP 시연 안정성을 위해 **STT/TTS 실행 UI를 코드 삭제 없이 플래그로 껐다**(`guide/ai-guide.js`의 `STT_TTS_ENABLED = false`). 이 문서에서 STT/TTS는 더 이상 "완료" 기능이 아니라 "프로토타입 구현·비활성화" 상태로 표기한다.

## 1. 프로젝트 한 줄 소개
가상의 모바일뱅킹 화면에서 고령자가 실제 돈 없이 송금을 처음부터 끝까지 스스로 연습하고, 막히면 AI 도움을 받을 수 있는 1일 해커톤 웹 MVP `금융한걸음`.

## 2. 문제 정의
(`SPEC.md` 3절 그대로)
1. 은행 업무가 모바일 중심으로 이동 중인데 고령자는 진입 단계에서 막힌다.
2. **연습할 방법이 없다** — 실제 뱅킹 앱은 잘못 누르면 실제 돈이 움직여서 "해보며 배우기"가 불가능하다.
3. 옆에서 알려줄 사람이 항상 있지 않고, 한 번 배워도 혼자 하려면 기억이 안 난다.

## 3. 기획 의도
- SPEC 1절에 명시된 핵심 방향: **"AI가 대신 해주는 서비스"가 아니라 "스스로 할 수 있게 가르쳐주는 서비스"** — AI는 사용자 대신 버튼을 누르지 않고 설명·안내·피드백만 한다.
- 대상 사용자(SPEC 2절): 스마트폰은 쓰지만 모바일뱅킹은 처음/서투른 고령자. 예시 상황으로 "아들이 계좌번호를 문자로 보내줬는데 어떻게 보내는지 몰라 은행 창구에 간다"를 든다.
- 실수해도 안전한 가상 환경 + AI가 "옆에서 알려주는 사람" 역할을 대신하며 반복 연습 가능하게 하는 것이 목표.

## 4. 서비스 사용자 흐름

**실제 코드(`screen/bank-ui.html`, `SCREENS` 배열 9개: intro/home/bank/account/amount/confirm/done/glossary/quiz) 기준 확인된 흐름:**

```
[미션 안내(intro)] → [내 계좌(home)] → [은행 선택(bank)] → [계좌번호(account)]
  → [금액(amount)] → [확인(confirm)] → [완료(done)] → (선택) [용어 복습하기 → O·X 퀴즈(quiz)]

[미션 안내(intro)] → (선택) [쉬운 금융 용어 사전(glossary)] → [O·X 퀴즈(quiz)]
```

- `intro` 화면: "오늘의 미션"과 미션 제목·받는 계좌를 보여주고, 버튼 2개 — "송금 연습 시작"(`home`으로), "📖 금융 용어 퀴즈"(`glossary`로). 둘 다 `missions.json`에 없는 순수 화면 전환(`data-goto`)이라 미션 판정(`MissionEngine`)을 거치지 않는다.
- `home`부터 `done`까지 6단계는 `mission/missions.json`의 `steps` 배열과 1:1 대응하며, 오답 시 화면이 넘어가지 않고(F8) 정답 시에만 다음 단계로 진행한다.
- `confirm`/`done` 화면의 은행명·계좌번호·금액은 화면 자체(`fillMissionValues()`)가 `MissionEngine.getMission()`에서 실시간으로 읽어와 채운다 — 화면 코드에 값이 하드코딩돼 있지 않다.
- **용어 사전(`glossary`)**: 5개 묶음(로그인·인증서·송금/계좌·보안·앱 편의기능) 안에 용어 20개, `<details>`로 접어서 노출. 맨 아래 "O·X 퀴즈 풀러 가기" 버튼으로 `quiz` 화면 진입.
- **O·X 퀴즈(`quiz`)**: 완료 화면의 "용어 복습하기"(`#quiz-start`) 또는 용어 사전 맨 아래 버튼, 두 경로로 진입 가능. 문항 10개, 한 화면에 한 문제, 답한 뒤 문제 위 카드에 정답·해설 표시, 오답이어도 재선택 불가(설명 후 다음 문제)로 정책이 확정돼 있다(`mission/quiz.js`). 끝나면 항상 "처음 화면으로"(`intro`)로 나간다 — 완료 화면에서 들어왔어도 완료 화면이 아니라 인트로로 복귀.
- **STT/TTS(F12/F11)**: 구현은 존재하지만 **발표용 MVP에서는 비활성화**돼 있다(`STT_TTS_ENABLED = false`). 마이크 버튼(`#mic-button`)은 항상 숨겨져 있고, AI 답변의 음성 낭독(`speechSynthesis`)도 호출되지 않는다 — 지금 화면에서는 텍스트 질문·답변만 동작한다.

| **`shared/llm-config.js` 콘솔 404 제거 (수정 완료)** | 존재하지 않는 파일을 불러오던 `<script src="../shared/llm-config.js">` 태그를 `screen/bank-ui.html`에서 삭제. 콘솔 404가 실제로 사라졌는지는 브라우저 개발자도구로 사람이 확인해야 함(정적 코드 검토로는 원인 제거만 확인됨) |

### 프로토타입으로 구현됐으나 발표용 MVP에서는 비활성화
| 기능 | 실제 상태 |
|---|---|
| **STT 음성 질문 (F12)** | `guide/voice.js`가 `SpeechRecognition`/`webkitSpeechRecognition` API와 `getUserMedia` 마이크 권한 확인까지 구현돼 있다. **실제 Chrome QA 결과**: "🎤 듣고 있어요…" 상태까지는 정상 진입하지만, 발화가 끝난 뒤 인식된 transcript가 답변 처리로 안정적으로 이어지지 않는 문제가 확인됐다. 추가 디버깅 대신 시연 안정성을 우선해 비활성화하기로 결정 |
| **TTS 답변 낭독 (F11)** | `guide/ai-guide.js`의 `speak()`가 `speechSynthesis`로 답변을 읽어주도록 구현돼 있다. **실제 Chrome QA 결과**: 음성 출력 자체는 되지만 문장 앞부분이 잘려 들리는 문제가 남아 있다(코드 수정을 이미 한 차례 시도했으나 실제 환경에서 완전히 해소되지 않음). 시연 안정성을 위해 비활성화 |
| **비활성화 방식** | 코드 삭제·구조 변경 없이 `guide/ai-guide.js` 상단에 `var STT_TTS_ENABLED = false;` 플래그 한 줄을 추가하고, 마이크 버튼 노출 조건과 `speak()` 호출 두 지점만 이 플래그로 감쌌다. 마이크 버튼(`#mic-button`)은 HTML의 `hidden` 속성이 그대로 유지되어 화면에 노출되지 않는다. 이 플래그를 `true`로 되돌리면 STT/TTS를 다시 켤 수 있다 — 향후 브라우저별 안정화 작업의 시작점으로 코드는 그대로 보존돼 있다 |

| 기능 | 실제 동작 수준 |
|---|---|
| **텍스트 질문 응답("AI 도움")** | 사용자가 적은 질문을 `guide/qa-data.json`의 **키워드 목록과 문자열 포함 매칭**으로 비교해 미리 써둔 문장을 돌려준다. 외부 LLM·생성형 모델을 호출하지 않는다 — "AI가 이해해서 답한다"가 아니라 "키워드가 맞으면 미리 정해둔 문장을 보여준다"에 가깝다 |

## 6. UI/UX 고려사항 (실제 `screen/bank-ui.html`·`styles.css` 확인 기준)
- **큰 글씨/큰 버튼**: 기본 버튼 높이 60px 이상, 폰트 20px 이상, 키패드 버튼 26px — 코드에서 확인됨
- **단계 단순화**: 한 화면에 한 가지 입력/행동만 요구(은행 3개 중 1개 선택 → 계좌번호 1개 입력 → 금액 1개 입력 → 확인)
- **안전 안내**: 상단 고정 헤더(`#app-header`)에 "교육용 연습 화면 · 실제 돈은 움직이지 않습니다"가 모든 화면에서 상시 노출, 완료 화면에도 "실제 돈은 움직이지 않았습니다" 재확인 문구
- **미션 제시 방식**: `screen-intro`에서 미션 제목을 한 번 보여준 뒤, 실제 연습 화면들(`home`~`done`)에는 정답 값(계좌번호·금액·은행명)을 직접 노출하지 않고, 확인/완료 화면에서만 사용자가 입력한 결과를 `missions.json` 기준으로 다시 보여준다
- **잘못 눌렀을 때 피드백(F8)**: 화면 이동 없이 해당 화면이 짧게 흔들리고(`.shake`), `#ai-answer`에 오답 문구가 빨간 계열(`.is-error`) 카드로 표시되며 다시 선택 가능
- **일반 AI 답변/오답 색상 분리**: `showAnswer()`(정보)는 기본 스타일, `showError()`(오답)만 `.is-error` 클래스를 추가해 색을 구분 — CSS에서 실제로 다른 배경/글자색 적용 확인
- **F5 숫자 키패드**: 물리 키보드 없이 화면 숫자 버튼만으로 계좌번호·금액 입력 가능, 금액은 입력 중 천 단위 쉼표 자동 표시(판정은 숫자만 비교하므로 무관)
- **용어 사전/퀴즈**: 색은 A의 `:root` 토큰(`--info-bg`·`--success-bg`·`--error-bg`·`--accent`)만 재사용해 다크모드도 그대로 따라가고, `screen/styles.css`(A 소유)는 건드리지 않고 `quiz.js`가 자체 `<style>`을 주입하는 방식으로 폴더 소유권을 지켰다

## 7. 기술 구성 (실제 코드 기준, 과장 없이)
- **Frontend 구조**: 프레임워크 없는 순수 HTML/CSS/바닐라 JS 파일(`screen/bank-ui.html`, `mission/*.js`, `guide/*.js`) + JSON 데이터 파일(`missions.json`, `quiz-data.json`, `qa-data.json`). 빌드 도구 없음, `<script src>` 순서 로딩(`mission-engine → voice → ai-guide → quiz`)
- **미션 상태 관리**: 전역 `window.MissionEngine`이 클로저 내부 변수(`current`)로 현재 단계를 들고 있고, `missions.json`을 `fetch`로 불러와 판정 규칙으로 씀. 서버/DB 없음, 새로고침하면 초기화됨
- **도움 기능 구조**: `window.AIGuide.askAI(question, step, mission)` 하나의 함수. 내부는 `guide/qa-data.json`을 `fetch`(1회 캐시) → 키워드 매칭 → 실패 시 `mission.steps`의 `wrong` 필드 → 그래도 없으면 고정 기본 문구. Promise 기반이며 절대 reject하지 않도록 설계
- **STT/TTS는 구현은 있지만 꺼져 있음**: `guide/ai-guide.js` 상단의 `STT_TTS_ENABLED = false` 플래그 하나로 마이크 버튼 노출과 `speechSynthesis` 낭독 호출을 막아 둔 상태. `window.Voice.startListening(onResult, onError)`(브라우저 내장 `SpeechRecognition` + `getUserMedia` 권한 확인 래퍼)와 `speak()`(TTS) 함수 자체는 그대로 코드에 남아 있어, 플래그만 `true`로 되돌리면 재활성화 가능
- **퀴즈 구조**: `window.Quiz`가 `#screen-quiz`의 DOM을 직접 그리고 지운다(다른 화면처럼 `bank-ui.html`에 고정 마크업이 있는 게 아니라 전부 `quiz.js`가 런타임에 생성)
- **데이터 파일**: `mission/missions.json`(미션 1개, 6단계 스키마), `mission/quiz-data.json`(O·X 10문항), `guide/qa-data.json`(단계별 키워드-답변 목록)
- **외부 API/LLM 사용 여부**: **없음.** `shared/llm-config.js`가 저장소에 존재하지 않고, 코드는 그 파일이 없을 때를 전제로 로컬 폴백만 타도록 짜여 있음
- **Fallback 여부**: 있음 — LLM 미연결 상태를 기본값으로 가정하고 설계된 구조 자체가 이 프로젝트의 핵심 폴백 전략

## 9. 개발 중 문제와 해결 (발표 가치가 있는 것만)

**1) 인터페이스 계약을 먼저 정하지 않으면 병렬 개발이 막힌다**
→ 어떻게 확인: 실제로 팀원이 모이기 전 A가 화면 작업을 마치고 보니 버튼을 눌러도 화면이 안 넘어감(`CHANGELOG-INBOX/0819-1440-영원.md`)
→ 어떻게 해결: S0 단계에서 `shared/CONTRACT.md`를 먼저 만들고, 아직 없는 `mission-engine.js`/`ai-guide.js`/`voice.js`를 "함수 이름만 계약과 맞으면 나중에 통째로 교체 가능한 스텁"으로 A가 대신 작성 → B/C가 합류해 실제 로직으로 교체(PR #9, #8)

**2) 로컬 검증 서버가 꼬여 최신 UI가 반영 안 된 것처럼 보인 문제**
→ 어떻게 확인: `netstat`로 확인해보니 이전 세션들에서 켠 `python -m http.server 8000` 프로세스가 5개나 동시에 남아 있었고, 그중 일부가 예전 임시 검증 폴더를 서빙 중이었음
→ 어떻게 해결: 좀비 프로세스를 전부 종료하고 프로젝트 루트에서 서버 1개만 새로 실행 → 서빙되는 파일의 md5를 로컬 `develop` 파일과 직접 비교해 최신본이 맞는지 검증

**3) F6(미션 데이터 분리) 수정이 F13(AI 도움)을 새로 깨뜨렸다가 다시 고쳐진 문제**
→ 어떻게 확인: `guide/qa-data.json`에 계좌번호·금액·은행명을 직접 하드코딩해뒀던 게 발견돼(F6 위반) 제거했는데, 그 직후 A가 크롬에서 재검증하다가 "계좌번호가 뭐예요?" 같은 흔한 질문에 값 없는 일반 안내만 나오는 걸 발견(`CHANGELOG-INBOX/0819-1530-영원.md`)
→ 원인: 키워드 매칭이 `missions.json` 기반 폴백보다 먼저 실행되도록 짜여 있어서, 흔한 키워드가 이미 등록돼 있으면 폴백까지 못 감
→ **어떻게 해결**: 팀 대표 권한으로 A가 `guide/`(원래 C 소유)를 예외적으로 직접 수정 — `qa-data.json`에서 문제가 된 넓은 키워드 항목만 삭제해 `fromMission` 폴백이 살아나게 함(`CHANGELOG-INBOX/0819-2010-영원.md`). 브라우저 재확인까지 끝난 상태라 **해결 완료**로 다뤄도 된다
→ **이후 QA에서 발견된 인접 이슈도 해결**: "다시 설명해주세요" 버튼이 은행/계좌/금액 단계에서 `fromMission`의 "오답 시" 문구를 실수 전에 노출하던 문제를, 해당 세 단계의 `qa-data.json`에 중립 키워드 항목을 추가해 수정했다(5절 완료 목록 참고). Node 시뮬레이션으로 검증했고, 실제 브라우저 확인은 남아 있다

**4) B(미션 로직)가 스텁인 동안은 통합 테스트가 의미 없었던 문제**
→ 어떻게 확인: mission-engine.js가 스텁일 때는 아무 버튼이나 눌러도 무조건 다음 단계로 넘어가, 오답 회복(F8) 같은 핵심 기능을 테스트해도 항상 "성공"으로 보임
→ 어떻게 해결: B의 실제 상태머신 구현(PR #9)이 병합된 뒤에야 오답 케이스(틀린 은행 선택, 틀린 금액 등)를 실제 로직으로 재검증

**5) 같은 기능(F16 퀴즈)을 통합자와 B가 동시에 만들어 충돌한 문제**
→ 어떻게 확인: 통합자가 임시로 5문제 객관식 버전을 먼저 만들어 PR을 올렸는데, 거의 같은 시각 B가 `feature/finquiz-lingo`(PR #11)로 O·X 10문제 정식 버전을 이미 develop에 병합함
→ 어떻게 해결: 통합자의 임시 버전은 rebase로 폐기하고 B의 실구현을 채택 — 담당 폴더(`mission/`)의 실제 구현을 우선하는 것으로 정리

**6) STT/TTS를 실제 Chrome에서 QA하니 코드 수정만으로는 시연 안정성이 확보되지 않은 문제**
→ 어떻게 확인: TTS 잘림 문제를 코드로 한 차례 수정했으나(불필요한 `cancel()` 제거, `getVoices()` 예열) 실제 Chrome에서 재확인하니 여전히 문장 앞부분이 잘렸고, STT는 "듣고 있어요…" 상태 이후 인식 결과가 답변 처리로 이어지지 않는 문제가 새로 확인됨
→ 어떻게 해결: 발표일이 임박한 상황에서 추가 디버깅에 시간을 더 쓰기보다 **시연 안정성을 우선**하기로 결정 — 구현 코드는 삭제하지 않고 `STT_TTS_ENABLED` 플래그 하나로 실행 UI만 껐다. 발표 이후 브라우저별 안정화 작업을 이어갈 수 있도록 코드베이스는 그대로 보존
→ 발표 가치: "완벽하게 안 되는 기능을 억지로 보여주기보다, 문제를 발견하면 범위를 좁혀 안정적인 것만 시연한다"는 판단 자체가 팀의 QA 프로세스를 보여주는 사례로 쓸 수 있음

## 10. 데모 추천 흐름 (현재 실제로 동작하는 것만)

**메인 흐름 (1~2분)**
1. `intro` 화면에서 "오늘의 미션: 김민수에게 50,000원 보내기" 확인 → **송금 연습 시작**
2. 홈에서 **이체** 클릭 (거래내역은 건드리지 않음)
3. 은행 선택에서 일부러 **새봄은행**(오답) 클릭 → 화면이 안 넘어가고 흔들리며 오답 설명 표시 → **한걸음은행** 클릭해 정답으로 진행
4. 계좌번호 화면에서 키패드로 숫자 입력 → 다음
5. 금액 화면에서 키패드로 `50000` 입력(쉼표 자동 표시 확인) → 다음
6. 확인 화면에서 은행명·계좌번호·금액이 실제 입력값 기준으로 채워진 것 확인 → 보내기
7. 완료 화면에서 "실제 돈은 움직이지 않았습니다" 확인
8. 홈 화면(2단계)에서 **💬 AI 선생님에게 물어보기** 클릭 → 질문칸에 짧은 질문(예: "다음에 뭘 눌러요") 입력 → 화면에 텍스트 답변이 뜨는 것 확인
9. (선택, Should 기능 시연) 완료 화면의 "용어 복습하기" 또는 인트로의 "📖 금융 용어 퀴즈" → 용어 사전에서 아무 묶음이나 펼쳐 보이기 → 맨 아래 "O·X 퀴즈 풀러 가기" → 문제 1~2개만 답해서 정답/해설 카드 확인

**과거에 있었던 시연 함정, 지금은 코드 수정으로 해결됨(실제 브라우저 재확인은 아직)**
- 은행/계좌/금액 단계에서 "다시 설명해주세요"를 눌러도 더 이상 실수 전에 오답 문구가 뜨지 않는다 — 이제 아무 단계에서나 이 버튼을 시연에 써도 된다
- 은행/계좌/금액/확인 화면에서 "← 처음으로"를 누른 뒤 홈에서 "이체"를 다시 눌러도 더 이상 화면이 이전 단계로 되돌아가지 않는다 — 처음부터 다시 보여줄 때 "다시 연습하기"뿐 아니라 "← 처음으로"도 안전하게 쓸 수 있다
- 다만 위 두 가지는 Node로 로직만 검증했고 실제 브라우저 클릭으로는 아직 확인하지 않았으니, 발표 전에 한 번은 직접 눌러서 재확인할 것(4절 "사람이 마지막으로 확인해야 할 항목" 참고)

**시연에서 빼야 할 것**
- **🎤 마이크 버튼 / "말로 물어보기" / 음성 낭독(TTS) 전체.** 발표용 MVP에서는 `STT_TTS_ENABLED = false`로 꺼져 있어 마이크 버튼 자체가 화면에 보이지 않는다. 실제 Chrome QA에서 TTS 잘림·STT 인식-답변 연결 불안정이 확인됐기 때문에 의도적으로 뺐다 — 시연 중 "음성으로도 물어볼 수 있다"처럼 언급하지 말 것. AI 도움은 **텍스트 질문 입력**으로만 시연할 것

- 문제 정의(2절) — 왜 이 서비스가 필요한지 짧게
- 기획 의도(3절) — "AI가 대신 해주는 게 아니라 스스로 하게 가르친다"는 한 문장
- 서비스 흐름(4절) — 실제 데모와 함께
- 핵심 구현(5절 완료 목록) — 특히 F7(판정)·F8(오답 피드백)·F17(진행 표시)·F16(용어사전+퀴즈)은 실제 동작하는 핵심 차별점
- 협업 방식(8절) — CONTRACT 먼저 정하고 병렬 개발한 것은 1일짜리 3인 프로젝트에서 나온 구체적 방법론이라 발표 가치가 큼
- 최종 결과 + 한계(5절 부분구현, 특히 "다시 설명해주세요" 이슈는 "다음 스텝"으로 정직하게 언급)

## 12. 시간이 부족하면 뺄 내용
- Git 브랜치 전략 세부(feature/develop 구조)는 한 줄로 축약 가능
- CHANGELOG-INBOX 쪽지 시스템 같은 운영 디테일은 "교차 확인 기록을 남겼다" 정도로 축약
- 기술 스택(7절)의 세부 구현 방식(캐시 1회, Promise 구조 등)은 질문 나올 때만 답변

## 13. 사용 시 주의할 표현
- **"AI 선생님"/"상황인지 AI"**: 코드상 UI 버튼 라벨(`💬 AI 선생님에게 물어보기`)로만 쓰인 문구다. 실제 동작은 키워드 매칭 + 미리 쓴 문장 폴백이므로, 이걸 "AI가 상황을 이해해서 답한다"처럼 설명하면 과장이다. "AI"라는 단어를 쓰려면 반드시 "지금은 규칙 기반 로컬 응답이고, LLM 연결은 아직 안 했다"를 같이 말해야 함
- **"실제 AI"라고 표현 가능한가**: 아니다. 외부 LLM 호출 코드/설정이 저장소에 전혀 없다(`shared/llm-config.js` 없음)
- **"음성 대화가 된다"**: 아니다. STT/TTS 구현 자체는 있지만 실제 Chrome QA에서 안정성 문제(TTS 잘림, STT 인식 후 답변 미연결)가 확인돼 **발표용 MVP에서는 꺼져 있다**. "음성으로 질문하고 들을 수 있다"처럼 현재형으로 말하면 사실과 다르다 — 말하려면 "음성 기능은 프로토타입으로 구현했지만 아직 불안정해 이번 시연에서는 텍스트로만 보여준다"고 정확히 표현할 것
- **"실제 모바일뱅킹과 동일하다"**: 과장. 화면 흐름과 입력 방식만 참고했을 뿐(SOL뱅킹 UI 레퍼런스), 실제 은행 앱의 보안(비밀번호/OTP), 잔액 반영, 거래내역 등은 의도적으로 제외됨(SPEC 4.3 확정 사항)
- **"용어 퀴즈 기능이 있다"**: 이제는 사실이다(PR #11로 완료). 다만 "10문제 O·X" 형식이라는 것까지 정확히 말할 것 — SPEC 초안의 "객관식 3~5문제"와 다르게 확정됐다는 점은 굳이 안 밝혀도 되지만, 틀린 형식(예: "객관식 퀴즈")으로 설명하지는 말 것
- **"팀이 Issue로 작업을 추적하고 완료 처리했다"**: 절반만 사실. Issue는 만들었지만 전부 OPEN 상태로 남아 있음 — "Issue로 작업을 나눴다"까지만 말하는 게 안전
- **"모든 버그를 다 고쳤다"**: 이번에 고친 것은 QA에서 발견된 특정 이슈 3건("← 처음으로" 상태 미초기화, "다시 설명해주세요" 선제적 오답, `llm-config.js` 콘솔 404)이다. 이 세 건은 Node 로직 시뮬레이션으로 검증됐지만 **실제 브라우저 클릭·렌더링으로는 아직 확인되지 않았다** — "완전히 검증됐다"처럼 말하지 말고 "코드로 확인했고, 실제 화면 재확인이 남아 있다"고 정확히 말할 것

### 발표자료 제작자에게 전달할 핵심 사실 10개

1. 이 서비스는 "AI가 대신 해주는" 게 아니라 "스스로 하게 가르치는" 것이 기획 의도의 핵심이다.
2. 실제 흐름은 미션 안내 → 은행 홈 → 은행 선택 → 계좌번호 → 금액 → 확인 → 완료, 6단계 미션 + 선택적 용어사전/퀴즈다.
3. 정답/오답 판정, 오답 시 화면 고정+흔들림+설명, 진행 단계 표시(n/4)는 전부 실제로 동작한다.
4. 금융 용어 사전(20개 용어)과 O·X 퀴즈(10문제)는 실제로 구현·병합돼 있다(PR #11) — 완료 화면과 인트로 화면 양쪽에서 들어갈 수 있고, 발표용 MVP에도 그대로 켜져 있다.
5. 음성 질문(STT)과 음성 낭독(TTS)은 프로토타입으로 구현·병합됐지만(PR #12), **실제 Chrome QA에서 TTS 잘림·STT 인식-답변 연결 불안정이 확인돼 발표용 MVP에서는 비활성화**했다. 코드는 삭제하지 않고 플래그(`STT_TTS_ENABLED`)로만 껐다 — "음성 기능이 있다"고 현재형으로 말하지 말 것.
6. "AI 도움"은 여전히 100% 로컬 키워드 매칭 + 미리 써둔 문장이다(텍스트 질문만). 외부 LLM은 한 번도 연결된 적이 없다.
7. 팀은 폴더 단위(screen/mission/guide)로 역할을 나누고, 공통 인터페이스 계약(CONTRACT.md)을 먼저 정한 뒤 병렬 개발했다.
8. 기능 PR 6건(#7~#12)이 모두 develop에 병합됐고, 중간중간 UI 재설계는 develop에 직접 커밋됐다(둘 다 프로젝트가 허용한 방식).
9. QA에서 발견됐던 문제 3건 — "계좌/금액 값이 안 나오는 회귀"(과거 해결), "다시 설명해주세요의 선제적 오답 문구", "← 처음으로 클릭 후 상태 미초기화" — 는 모두 코드 수정으로 해결됐다. 단, 뒤의 두 건은 Node 로직 시뮬레이션으로만 검증됐고 실제 브라우저 확인은 아직 남아 있다.
10. Issue 6개는 만들어졌지만 전부 OPEN 상태로 남아 있어, "Issue로 완료까지 관리했다"는 표현은 쓰면 안 된다.
11. 발표 담당자가 STT/TTS 프로토타입 화면(마이크 버튼, "듣고 있어요…" 상태)을 캡처하고 싶다면, `STT_TTS_ENABLED`를 임시로 `true`로 바꾼 로컬 환경에서 직접 캡처해야 한다 — 이 세션에는 브라우저/스크린샷 도구가 없어 캡처를 만들어내지 못했다.
